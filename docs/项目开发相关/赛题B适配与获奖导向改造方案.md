# StudyMate 面向“揭榜挂帅-云之脑”赛题 B 的适配与获奖导向改造方案

> 赛题编号：XH-202630
>
> 赛题名称：领域知识个性化生成与多智能体协同决策系统研究
>
> 文档性质：总体改造方案；具体实现状态以“实施进度”与应用文档为准
>
> 分析日期：2026-08-07

## 实施进度（2026-08-08）

第一阶段闭环已经落地：领域/目标岗位映射、学情诊断、定制讲义/实操指南/分阶测试三类生成、事实来源/实操规范/难度覆盖三项审核、总裁决、一次定向自动返工、发布门禁、运行审计记录和答题反馈更新均已实现。前端已展示阶段、八个核心 Agent、诊断结论、审核分数、纠偏条数、裁决与返工轮次，并在发布前锁定资源。

仍未完成的赛题验证工作包括：职业技能画像扩展、工业视觉专用资料与案例深加工、50 组以上真实标注评测集、幻觉率/难度适配准确率/知识点覆盖率实验看板，以及至少三组差异化参赛画像。闭环用法见[岗位训练闭环使用指南](../../studymate/docs/岗位训练闭环使用指南.md)。

## 1. 结论先行

StudyMate 与赛题 B 的基础重合度较高，现有画像、课程 RAG、资源生成、测验、学习报告、反馈、Agent 状态展示和测试管理均可复用，不建议重写系统。最合适的路线是在现有“高校课程学习平台”外增加一个“垂直领域技能训练模式”，将核心叙事从“多种学习资源生成”升级为“多智能体对专业内容进行生成、质检、裁决和动态重生成”。

真正决定赛题 B 竞争力的不是继续增加资源种类、数字人或动画数量，而是补齐以下五项能力：

1. 把现有“检索后多个资源 Agent 并发生成”改成可观测的“诊断 → 规划 → 生成 → 交叉验证/辩论 → 裁决 → 反馈更新”状态图。
2. 新增独立的领域专家、事实核验、规范/安全审核和裁决角色，让系统能够拒绝无依据内容、触发返工并保留完整证据链。
3. 把面向大学课程的画像扩展为面向职业技能训练的证据型画像，明确学历/专业、岗位目标、从业经验、工具环境、先验测试和技能掌握度。
4. 建设一个可演示、可测试的垂直领域知识库切片，并生成“定制讲义、实操指南、分阶测试”三类赛题点名要求的资源。
5. 建立独立评测集和指标看板，用真实标注证明幻觉率 `<5%`、画像-资源难度适配准确率 `≥85%`、核心知识点覆盖率 `≥90%`，不能只依赖 LLM 自评。

推荐把首个垂直领域定为“工业视觉质检模型开发与部署”。它与现有机器学习、代码案例、可视讲解和在线运行能力衔接紧密，同时比泛化的“AI 学习平台”更能体现岗位技能、工程实操、行业规范和错误风险。如果团队无法取得足够可靠的工业资料与专家标注，可退而选择“企业级 RAG 应用开发与质量保障”，但主演示必须始终聚焦一个具体岗位任务，不能只展示通用聊天和课程资源。

## 2. 分析依据与口径纠正

本方案依据以下材料形成：

- 官方赛题文件《XH-202630上海云之脑智能科技有限公司-领域知识个性化生成与多智能体协同决策系统研究比赛方案.pdf》。
- 对比材料《三个赛题对比分析.html》。
- 当前项目的[系统架构](../../studymate/docs/系统架构.md)、[接口说明](../../studymate/docs/接口说明.md)与[开发计划](plan.md)，并核对了实际前后端代码。

需要特别纠正：对比 HTML 中写到赛题 B “未公布详细评分标准”，但官方 PDF 已明确给出百分制评分：作品完整性 30 分、技术创新性 25 分、用户体验 15 分、实用价值 30 分。因此开发优先级必须同时服务于闭环完整性与可量化实用价值，不能只强调多智能体概念。

官方材料中与数据规模有关的三个层次也需要区分：

- 提交形式的最低要求：至少 1 个垂直领域知识库切片，以及不少于 2 组差异化学习者初始学情数据。
- 实用价值满分描述：至少 1 个垂直领域知识库，以及至少 3 组不同背景学习者画像。
- 扣分描述：测试用例不足 50 组会被视为测试方案不完整。

为冲击高分，交付基线应按更严格口径准备：`1 个可审计垂直知识库 + 至少 3 类学习者画像 + 不少于 50 个测试场景`，建议最终准备 60 个以上测试场景。

## 4. 推荐的产品定位与演示领域

### 4.1 新的产品定位

建议在保留 StudyMate 品牌的前提下增加副标题：

> StudyMate SkillOps：面向垂直岗位技能的多智能体个性化训练与质量决策平台

对外叙事应从“为学生生成多种学习资源”调整为：

> 系统先根据学习者背景和先验测评定位技能盲区，再由领域专家 Agent 依据版本化专业知识库生成训练资源，由事实核验与规范审核 Agent 提出异议，最终由裁决 Agent 依据证据和质量阈值决定通过、返工、降级解释或转人工复核；学习行为与测试结果再驱动下一轮资源更新。

原有“高校课程模式”不必删除，可作为通用能力证明；比赛演示默认进入“技能训练模式”。

### 4.2 首选领域：工业视觉质检模型开发与部署

建议将主岗位定义为“工业视觉质检算法/应用工程师”，围绕一个可闭环的任务组织知识库与资源：从缺陷数据理解、数据质检、模型训练、指标判断，到部署约束、异常排查和效果复盘。

至少准备三类学习者：

| 学习者 | 典型背景 | 主要盲区 | 系统应输出的差异 |
| --- | --- | --- | --- |
| A：高职智能制造新手 | 熟悉产线与设备，编程和机器学习较弱 | Python、数据集、分类/检测基本概念 | 更短步骤、术语解释、可视示例、低代码实践和基础题 |
| B：计算机本科生 | 编程与算法较强，不熟悉工业现场 | 缺陷定义、误检漏检成本、数据采集与部署约束 | 弱化基础代码，强化行业规范、指标权衡和现场案例 |
| C：制造业转岗工程师 | 有工艺经验和少量脚本能力 | 模型评估、部署、漂移与故障诊断 | 面向岗位任务的 SOP、检查表、风险点和进阶挑战 |

三组人使用同一主题时，输出必须在前置知识、解释粒度、示例、工具要求、题目难度和路径顺序上产生可解释差异，而不是仅改变措辞。

### 4.3 知识库切片的组成

知识库不要仅放教材段落。每个来源应记录 `domain`、`task`、`skill`、`source_type`、`authority_level`、`version`、`effective_date`、`section`、`risk_level` 和 `reviewed_by`。建议包含：

1. 行业/团体/企业采用的规范与术语说明。
2. 经授权的设备或软件官方手册。
3. 数据采集、标注、训练、验收和上线 SOP。
4. 典型缺陷、错误案例、故障排查树和边界条件。
5. 由指导教师或企业导师审核的岗位任务清单与能力标准。
6. 可安全公开的示例数据、代码和预期输出。

高风险操作、版本过期或证据不足的内容必须显式标记，不能由模型自行补全。若无法取得真实设备环境，演示应明确使用仿真数据或离线案例，不得把模拟结果包装成真实产线验证。

## 5. 功能改造详案

### 5.1 建立“领域—岗位—技能任务—能力点”模型

当前 `Course` 主要表达课程范围。建议在其上增加职业训练语义，而不是直接把课程名称改成岗位：

- `Domain`：垂直领域，例如工业视觉质检。
- `JobRole`：目标岗位，例如质检算法应用工程师。
- `SkillTask`：可执行岗位任务，例如“构建缺陷数据集”“选择验收指标”“排查漏检”。
- `Competency`：原子能力点，含等级、前置关系、核心/可选标记和权重。
- `CompetencyEvidence`：掌握证据，来源于先验测试、代码运行、题目、人工确认或历史任务。

现有 `Course` 可继续作为知识库与 UI 分组；新增表通过 `course_id/domain_id` 关联。前端课程卡在技能模式下展示岗位、任务数、目标级别和知识库版本。

验收标准：评委可以从岗位进入任务，再看到每个任务所需能力、当前掌握度、证据和对应训练资源。

### 5.2 将学习画像升级为“证据型职业学情画像”

在 `backend/app/schemas/profile.py` 的 7 组画像基础上新增或重构以下信息：

- 背景事实：学历层次、专业方向、从业年限、当前岗位、目标岗位。
- 环境约束：可用设备、操作系统、编程语言、软件版本、每周时间和截止日期。
- 先验能力：按领域能力点记录 `mastery_level`、`confidence`、`evidence_ids` 和 `last_verified_at`。
- 训练偏好：阅读/视频/代码等偏好继续保留，但只影响呈现方式，不能覆盖专业正确性约束。
- 风险边界：是否允许连接真实设备、是否仅仿真、是否需要导师审核。
- 数据授权：画像数据用途、授权时间、撤回状态和保留期限。

当前知识基础默认值为 3，适合作为 UI 中性初值，但在比赛的证据型画像中容易被误解为“已确认的中等水平”。建议将“未知”与“评分 3”分开：没有证据时显示“待诊断”，不能参与准确率统计或被当作真实能力。

新增诊断流程：

1. 结构化基础问卷获取背景与岗位目标。
2. 根据目标岗位自动生成 8-15 道先验测试，覆盖核心能力和必要前置。
3. 对代码/操作题记录执行结果、用时、错误类型和是否需要提示。
4. DiagnosisAgent 汇总为掌握概率、盲区、证据充分度和待确认项。
5. 用户确认画像后才进入生成；人工填写与模型推断必须有不同标识。

验收标准：任何画像结论都能展开查看“依据是什么”，且同一主题对三类学习者产生明显不同的难度与路径决策。

### 5.3 把多 Agent 改造成真正的协同决策状态图

现有 `backend/app/agents/orchestrator.py` 是“RAG 检索 → 多资源 Agent 并发 → 汇总”。建议升级为以下状态图：

```text
画像与先验测试
    ↓
DiagnosisAgent（盲区、目标、证据充分度）
    ↓
PlannerAgent（训练目标、资源类型、目标难度、核心知识点）
    ↓
DomainExpertAgent + RAG（生成领域事实与实操约束）
    ↓
ResourceAgents（讲义 / 实操指南 / 分阶题，可并发）
    ↓
EvidenceVerifierAgent ─┐
StandardSafetyAgent ───┼→ Debate/Review Findings
DifficultyReviewerAgent┘
    ↓
ArbiterAgent（通过 / 定向返工 / 降级解释 / 拒答 / 转人工）
    ↓                         ↑ 最多 2 轮
发布资源 → 学习交互 → FeedbackAgent → 更新画像与下一轮策略
```

建议角色职责如下：

| Agent | 输入 | 核心职责 | 必须输出 |
| --- | --- | --- | --- |
| DiagnosisAgent | 背景、先验测试、历史证据 | 定位盲区、掌握等级与证据不足项 | `diagnosis`、`confidence`、`knowledge_gaps` |
| PlannerAgent | 画像、岗位能力图、训练目标 | 决定目标能力、资源组合、目标难度和必覆盖知识点 | `training_contract` |
| DomainExpertAgent | 训练合同、领域 RAG | 只基于允许来源形成事实底稿、步骤约束和风险边界 | 原子主张与 evidence IDs |
| ResourceAgents | 事实底稿、画像、模板 | 生成讲义、实操指南和分阶测试 | 结构化资源草稿 |
| EvidenceVerifierAgent | 草稿、原文证据 | 检查每项专业主张是否被引用支持，发现冲突、过度推断和过期来源 | `review_findings`、groundedness |
| StandardSafetyAgent | 实操步骤、规范和风险规则 | 检查顺序、前置条件、安全提示、禁用操作和合规性 | 阻断项与修订建议 |
| DifficultyReviewerAgent | 画像、题目/步骤、历史表现 | 判断是否过难、过易或前置缺失 | 难度偏差和调整建议 |
| ArbiterAgent | 所有审核意见和阈值 | 给出最终决策，明确接受哪些意见并决定返工目标 | `decision`、理由、下一状态 |
| FeedbackAgent | 答题、用时、提示、反馈 | 更新能力证据，并选择降阶、补前置、保持或进阶 | `adaptation_action` |

Agent 必须拥有不同的系统提示、工具权限、输入范围和结构化输出，不能只是把同一个模型连续调用几次后换名称。领域专家只读知识库，审核 Agent 不接收生成 Agent 的隐藏推理，只检查可见草稿和证据；裁决 Agent 只能依据结构化审核结论和确定性阈值作决定。

### 5.4 实现可验证的“交叉验证与辩论”

辩论不应做成多个模型互相闲聊。建议采用“问题单驱动”的结构化机制：

1. 审核 Agent 对具体资源片段提出 `finding`，包含严重度、原文位置、问题类型、证据和修改建议。
2. DomainExpertAgent 可以提供补充证据、接受问题或说明无法验证。
3. ArbiterAgent 按来源权威等级、证据蕴含关系和安全规则裁决。
4. 前端展示“发现问题 → 引用证据 → 生成方回应 → 最终裁决 → 修订前后差异”。

建议的确定性质量门禁：

- `safety_blockers == 0`，否则不得发布。
- 核心专业主张引用覆盖率 `>=95%`。
- 引用蕴含/一致性得分达到预设阈值，低于阈值定向返工。
- 核心知识点覆盖率达到当前训练合同要求。
- 资源难度落在目标区间内。
- 最多返工 2 轮；仍未通过时输出“证据不足，建议人工复核”，不能继续编造。

每次运行必须保存模型提供方、模型名、提示模板版本、知识库版本、检索 chunk、草稿版本、审核意见、裁决、耗时和错误。前端可以隐藏冗长技术字段，但评委模式必须能展开审计。

### 5.5 增加赛题明确要求的三类核心资源

现有资源类型可以保留，但比赛默认资源包至少固定包含以下三类：

#### A. 定制化讲义 `custom_lesson`

- 学习目标与适用画像。
- 必要前置知识及缺失时的补偿入口。
- 核心概念、岗位情境和反例。
- 关键主张逐条引用。
- 本资源的目标难度、预计时长和审核状态。

#### B. 实操指南 `practice_guide`

- 任务背景与验收标准。
- 环境、工具、数据和安全前置。
- 编号步骤，每步包含输入、操作、预期结果、验证方式和失败处理。
- 常见故障树、禁止事项、回滚方案。
- 可运行代码或仿真入口。
- 面向不同画像的提示层级，默认不直接泄露完整答案。

#### C. 分阶测试 `tiered_assessment`

- 基础、应用、进阶/挑战三级题目。
- 每题绑定能力点、难度、正确答案、评分 rubric 与来源。
- 除选择/填空外，至少包含一个岗位情境题或操作任务。
- 支持先测后学、学习后测和迁移测试，避免只复述讲义。

思维导图、阅读、视频、代码和可视讲解作为增强资源，而不是用来替代上述三类硬性资源。

### 5.6 让所有资源具备统一的来源和质量元数据

当前只有 DocAgent 明确返回 citations。建议所有资源统一返回：

```json
{
  "resource_type": "practice_guide",
  "target_competencies": ["competency-id"],
  "target_difficulty": 2,
  "suitable_profile": {"min_level": 1, "max_level": 2},
  "claims": [
    {"text": "...", "evidence_ids": ["chunk-id"], "risk": "medium"}
  ],
  "quality": {
    "groundedness": 0.97,
    "core_coverage": 0.93,
    "difficulty_fit": 0.88,
    "status": "approved"
  },
  "decision_id": "..."
}
```

题目答案、实操步骤、代码解释和路径节点都应能追溯来源。UI 中“有引用”与“已审核通过”必须分开展示：检索到来源不等于内容正确，审核失败的草稿不能进入正式资源库。

### 5.7 实现基于反馈的自动升降阶决策

在现有测验、错题标签、评估和画像回写之上增加每个能力点的掌握状态。首版可用可解释规则，后续再尝试 IRT/BKT：

| 证据 | 建议动作 |
| --- | --- |
| 正确率 `<60%` 或关键前置能力缺失 | `prerequisite_repair`：补前置知识并生成降维解释 |
| 正确率 `60%-84%` 且错误集中 | `targeted_practice`：针对错误类型生成同级变式训练 |
| 正确率 `>=85%` 且中高难度证据充分 | `advanced_challenge`：生成岗位情境进阶任务 |
| 结果波动大或证据不足 | `collect_more_evidence`：追加诊断题，不贸然改变画像 |
| 触发安全/规范错误 | `mandatory_review`：锁定进阶并要求复习或导师确认 |

一次答题不能直接大幅改变能力等级。应综合近期多次测试、难度、提示次数、用时和代码/实操结果，保存变化前后证据。学习者可以查看并撤销系统建议，培训管理者可以看到触发原因。

### 5.8 新建赛题 B 专用决策报告

现有 `Report.tsx` 的画像对比、主题×难度热力图和建议可直接复用。建议增加四个核心视图：

1. **知识盲区定位图**：岗位能力点 × 当前掌握度 × 证据置信度，标出核心阻塞项。
2. **资源难度匹配曲线**：横轴为学习路径阶段，展示学习者能力区间、资源难度及偏差；点击可看匹配理由。
3. **学习路径规划图**：节点绑定能力点、资源、先决条件、预计时长和通过条件，反馈后可看到路径调整。
4. **多智能体决策回放**：时间轴展示检索、生成、审核异议、返工与最终裁决，支持草稿 diff 和证据跳转。

管理者视图另增加：不同画像的匹配准确率、资源驳回率、最常见审核问题、知识库缺口和待人工复核队列。

### 5.9 补齐数据合规与伦理功能

比赛版本至少实现：

- 所有用户数据接口从 HttpOnly Session 获取身份，逐步移除客户端可指定任意 `user_id` 的路径。
- 首次画像采集前显示数据用途、采集范围和保留时间，保存明确同意记录。
- 区分用户填写、测试事实、系统推断和人工审核四类画像来源。
- 提供个人画像/学习记录导出与删除入口，撤回授权后停止用于个性化生成。
- 日志中使用内部用户 ID，不保存邮箱、姓名、附件原文等不必要信息。
- 演示与评测数据全部使用合成或脱敏画像；交付包附数据字典、来源和授权说明。
- AI 生成资源显示模型、生成时间、知识库版本和“AI 生成/已审核”状态。
- 对高风险实操内容保留免责声明和人工复核入口。

## 7. 三项官方指标的评测设计

### 7.1 幻觉率 `<5%`

建议把生成资源拆成可验证的原子专业主张，由领域专家对照金标准和来源标注：

```text
幻觉率 =（事实错误主张数 + 无来源却声称确定的专业主张数）/ 被抽检的专业主张总数
```

注意事项：

- “有 citation”不代表 citation 支持该主张，必须检查蕴含关系。
- LLM-as-judge 只能做预筛；正式结果至少由两名标注者独立判断，分歧由指导教师或领域专家裁决。
- 同时报告事实错误、无证据、来源冲突、过期内容和安全错误五类失败。
- 对高风险实操主张 100% 检查，对普通说明可分层抽样。
- 报告样本量、版本和置信区间，禁止只展示精选成功案例。

### 7.2 画像-资源难度适配准确率 `≥85%`

先由专家为每个测试画像和任务标注合适难度区间，再比较系统决策；同时用真实答题表现做后验验证：

```text
适配准确率 = 难度落入专家标注区间且未缺失关键前置的资源数 / 被评资源总数
```

后验可增加规则：学习者在无过度提示时达到约 `60%-85%` 的正确率通常说明难度具有挑战但可完成；过高可能过易，过低可能过难。该区间只能作为辅助证据，不能代替专家标注。

### 7.3 核心知识点覆盖率 `≥90%`

每个 `SkillTask` 先建立带权重的核心能力清单，再检查资源包是否准确覆盖：

```text
核心知识点覆盖率 = 已被合格资源覆盖的核心能力权重之和 / 目标核心能力权重之和
```

“提到关键词”不算覆盖。必须至少有解释、实操步骤或可评分题目之一，并通过证据审核。报告应同时给出遗漏项，驱动 PlannerAgent 定向补生成。

### 7.4 建议测试集

至少准备 60 个场景，覆盖三类画像与不同难度：

| 类别 | 建议数量 | 目的 |
| --- | ---: | --- |
| 领域事实与概念 | 15 | 测事实正确性、来源与冲突处理 |
| 实操步骤与故障排查 | 15 | 测 SOP、边界、安全与可执行性 |
| 画像难度适配 | 15 | 同题不同背景，测资源难度和路径差异 |
| 核心知识覆盖 | 10 | 测训练合同中的必备能力是否遗漏 |
| 对抗/证据不足 | 5 | 测过期来源、冲突证据、诱导编造和拒答 |

每个用例保存：输入画像、岗位任务、知识库版本、检索结果、Agent 中间输出、审核意见、裁决、最终资源、人工标签和三项指标。另做“当前单次生成基线 vs 新协同决策流程”的 A/B 对比，证明创新机制确实降低错误，而不是只增加调用次数。

## 8. 按评分标准组织开发与证据

| 评分项 | 应优先完成的功能 | 答辩时展示的证据 |
| --- | --- | --- |
| 完整性 30 分 | 画像→诊断→多 Agent→审核/裁决→资源→交互→动态更新全链路；异常、返工和部署可用 | 一条完整 run 回放、3 类资源、反馈后路径变化、单元/接口测试 |

## 9. 开发优先级

### P0：先拿到赛题合格线并形成完整演示

1. 建立一个垂直领域、一个目标岗位和 8-12 个核心能力点。
2. 增加 3 类差异化画像和先验诊断，修复“未知等于默认 3 分”。
3. 把 Orchestrator 改为至少包含 Diagnosis、DomainExpert、Reviewer、Arbiter 的有向闭环。
4. 固化定制讲义、实操指南、分阶测试三类资源协议。
5. 为所有资源增加来源、审核状态、适用难度和 decision ID。
6. 打通答题反馈后的降阶解释与进阶挑战两个分支。
7. 在报告中呈现盲区、难度匹配和学习路径。
8. 保存并导出完整 Agent 中间数据。
9. 修复主要用户所有权问题，增加画像采集同意。

### P1：冲击高分的核心建设

1. 完成 claim-evidence 核验、规范/安全审核和结构化辩论。
2. 实现定向返工、最多轮次、拒答和人工复核。
3. 建成 60 个以上 benchmark 场景与人工标注流程。
4. 实现三项官方指标、分画像切片、失败分类和基线对比。
5. 增加决策回放、修订 diff、知识库版本与来源权威展示。
6. 邀请领域教师/企业导师审核能力清单、知识库切片和测试标签。

### P2：时间充足再做的加分项

1. 企业培训管理者视图、班组画像与待审核队列。
2. 领域配置包导入/导出，演示迁移到第二个小领域。
3. 更正式的 IRT/BKT 掌握度模型和线上 A/B 实验。
4. 与真实仿真环境或受控设备沙箱对接。
5. 领域知识冲突发现、知识库缺口自动回传和专家修订工作流。

### 暂不优先

- 不要继续以增加数字人动作、资源数量或动画数量作为主要创新点。
- 不要为了“架构高级”直接引入 Neo4j、LangGraph 或更多模型；先证明现有状态图、关系表和质量门禁能达标。
- 不要把 7 个并发生成器直接宣传成多智能体协同决策。
- 不要宣称“零幻觉”；应展示可复现的 `<5%` 评测结果、失败样本和拒答机制。
- 不要仅用 LLM-as-judge 得出官方三项指标。

## 10. 建议的 10 分钟演示脚本

1. **0:00-0:40 痛点与领域**：说明同一工业视觉任务对三类学习者不能使用同一资源，且专业内容错误会带来实际成本。
2. **0:40-1:40 差异化画像输入**：选择高职新手，展示背景、先验测试、能力证据和知识盲区。
3. **1:40-2:20 训练合同**：系统明确本轮目标能力、三类资源、目标难度和必覆盖知识点。
4. **2:20-4:40 多 Agent 协同**：展示检索、领域底稿、资源生成、审核发现一个无依据步骤、生成方补证失败、裁决 Agent 定向返工。
5. **4:40-5:40 最终资源**：打开实操指南，检查步骤、预期结果、故障处理、逐条来源和审核章。
6. **5:40-6:40 交互反馈**：完成一组题，故意暴露前置知识缺口，系统选择“降维解释 + 补前置”；再展示高分画像会收到进阶挑战。
7. **6:40-7:40 决策报告**：展示知识盲区图、难度匹配曲线和调整后的学习路径。
8. **7:40-8:50 量化评测**：展示 60 个测试场景、三类画像和三项官方指标，打开一个失败样本说明系统如何拒答或返工。
9. **8:50-9:30 合规与审计**：展示画像授权、AI/审核标识、知识库版本和完整 run 导出。
10. **9:30-10:00 价值与迁移**：说明领域配置如何迁移到企业内训或转岗培训，并给出真实边界，不夸大尚未验证的能力。

### 功能闭环

- [ ] 至少 3 个具有独立输入、工具、提示和输出协议的真实 Agent。
- [ ] 可完整演示分析、生成、校验、决策、反馈和动态更新。
- [ ] 审核不通过能定向返工；证据不足能拒答或进入人工复核。
- [ ] 三类核心资源均可生成、审核、持久化和导出。
- [ ] 三类学习者对同一任务得到可解释的不同资源与路径。

### 可视化与体验

- [ ] 报告包含知识盲区、资源难度匹配曲线和学习路径图。
- [ ] Agent 协作过程能看到异议、证据、裁决与修订结果。
- [ ] 每个资源显示适用画像、难度、引用、知识库版本和审核状态。
- [ ] 10 分钟演示不依赖临时手工改库，不因单个外部 API 失败而中断。

### 测试与指标

- [ ] 至少 1 个垂直领域知识库切片，附来源、版本、授权和能力点映射。
- [ ] 至少 3 组差异化画像，完整保存输入、中间决策和最终输出。
- [ ] 至少 50 个、建议 60 个以上测试场景。
- [ ] 幻觉率 `<5%`，并有人工标注、失败分类和抽样说明。
- [ ] 画像-资源难度适配准确率 `≥85%`。
- [ ] 核心知识点覆盖率 `≥90%`。
- [ ] 单体/单次生成基线与多 Agent 方案有同数据集 A/B 对比。

### 工程与合规

- [ ] 核心调度、审核、返工、指标计算具有单元测试和接口测试。
- [ ] 所有中间状态可持久化、重放和导出，服务重启后不会伪装完成。
- [ ] 用户身份不再由普通客户端任意指定，画像与资源均校验所有权。
- [ ] 有画像授权、撤回、导出、删除、脱敏和保留期说明。
- [ ] 部署说明、测试数据、演示视频和设计文档与实际版本一致。

## 12. 推荐的最小获奖版本

如果开发时间有限，建议把范围严格控制为：

- 1 个领域：工业视觉质检。
- 1 个岗位：工业视觉质检算法/应用工程师。
- 3 类画像：高职新手、计算机本科生、制造业转岗工程师。
- 4 个核心决策角色：诊断、领域专家、审核、裁决；原有资源 Agent 作为执行角色继续复用。
- 3 类必备资源：定制讲义、实操指南、分阶测试。
- 2 个反馈动作：降维解释、进阶挑战。
- 3 个报告图：盲区、难度匹配、路径。
- 60 个可重复测试场景和三项官方指标。

这个版本比“扩充到更多行业、更多 Agent、更多多模态资源”更有获奖可能，因为它可以把赛题 B 的完整性、创新性、体验和实用价值四项评分全部落到可展示、可追溯、可测量的证据上。
