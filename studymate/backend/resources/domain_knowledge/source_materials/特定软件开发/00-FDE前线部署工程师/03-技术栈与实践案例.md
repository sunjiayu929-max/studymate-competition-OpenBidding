# 前线部署工程师（FDE）｜技术栈与实践案例

## 一、技术能力栈

**数据与集成：**FDE 需要能理解数据表、接口契约、身份权限和数据质量问题。Awesome-FDE-Roadmap 将数据工程列为 FDE 学习路线的第一阶段，并把企业数据架构和 RAG 作为应用 AI 的基础。[G1]

**平台与交付：**容器、云环境、配置管理、CI/CD、日志和可观测性用于把可运行方案交给客户环境。Awesome-FDE-Roadmap 将云架构/基础设施列为第二阶段；FDEOps 将交付阶段明确为 plan、build、ship、close，而不是只完成编码。[G1][G2]

**AI 应用：**企业 AI 场景需要识别模型、检索、工具调用与业务规则的边界。Palantir 的 AI FDE 官方文档提供了将 AI FDE 放入 Foundry 平台语境的入口；实际项目仍应按客户数据授权和平台能力实施。[S1]

**记录与协作：**FDEOps 的 `.fde/` fieldbook 用于保存一次交付中的客户事实、承诺、阶段和下一步，强调记录应有日期、来源并由工程师确认。[G2]

**国内真实 JD 的技术要求：**美团 CatPaw FDE 职位公开要求候选人掌握 Java/Spring Boot、Go、Python 或 React/TypeScript 之一，并具备微服务、API 设计、分布式系统、稳定性、性能和可观测性经验；同时理解 Prompt、Function Calling、RAG、Agent 编排和上下文管理。[J1]

## 二、开源实践案例

### 案例 1：FDEOps 交付记录

场景：客户会议后，需要把会议内容、承诺事项、阶段和待办转为可追踪资料。[G2]  
做法：按 land → discover → plan → build → ship → close 组织项目过程，会议记录只在人工确认后写入 fieldbook。[G2]  
可交付物：需求事实表、决策记录、待办清单、验收证据和交接摘要。[G2]

### 案例 2：FDE 路线图中的企业 RAG 交付

场景：客户希望把内部资料用于可控问答，但文档质量、权限和检索效果不确定。[G1]  
做法：先盘点数据与权限，再做小范围检索/引用原型，最后以代表性问题和用户反馈决定是否扩展；路线图把企业 RAG 和 LLM 系统评测列为 FDE 的应用 AI 主题。[G1]  
验收：答案能定位证据、无权限资料不进入上下文、失败样本被保留用于迭代。[G1]

### 案例 3：AI FDE 的平台协同

场景：组织需要把 AI 能力接入现有业务工作流，而非单独做聊天演示。[S1]  
做法：在客户环境中确认数据、平台、权限、业务动作与反馈闭环，逐步扩大可验证场景。[S1][S2]  
限制：公开文档只能说明平台能力和实践方向，具体客户指标、合同范围与安全策略必须以项目证据为准。[S1][S2]

### 案例 4：国内 AI FDE 从 POC 到生产

美团 CatPaw FDE JD 要求工程师把客户业务痛点转成可量化、可验证的 Agent 问题，为交付能力建立评测集、离线评分和线上效果监控；上线后跟踪采纳率、任务成功率、人工干预率和边缘案例，并完成客户培训与通用能力沉淀。[J1]

## 三、工具选择原则

工具应服务于客户现场问题，不应因为“技术先进”而替代需求澄清。选择数据、云、Agent、RAG 或可观测性工具前，应先确认客户环境是否允许、数据是否授权、运维责任归属和验收标准。[G1][G2][G3]

## 国内招聘技术栈证据

美团 CatPaw FDE 的职位明确列出 Java/Spring Boot、Go、Python 或 React/TypeScript 之一，以及微服务、API、分布式系统、稳定性、性能、可观测性、Prompt、Function Calling、RAG 和 Agent 编排；这是一条同岗位的国内技术栈样本，不应扩展为所有 FDE 的强制清单。[J1]

AI 应用、智能体应用开发、AI 智能体开发和金融 Agent 算法职位（J2-J7）构成 FDE 的相邻协作岗位样本。学习者应能区分“交付型 FDE”与“应用/算法研发”的职责差别，并根据客户项目实际选择语言、框架和模型能力。[J2][J3][J4][J5][J6][J7]
