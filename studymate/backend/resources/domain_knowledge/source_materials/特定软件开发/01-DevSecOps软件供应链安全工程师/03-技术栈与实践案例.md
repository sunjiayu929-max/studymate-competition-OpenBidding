# 软件供应链安全工程师（DevSecOps）- 03 技术栈与实践案例

**软件供应链格式：**SPDX 是 SBOM 交换标准之一，CycloneDX 是面向软件供应链安全场景的 SBOM 标准之一。 [S1][S2]

**来源证明：**SLSA 定义了构建来源证明等供应链安全概念；工程实现可通过 Sigstore/Cosign 对制品签名。 [S3][G1]

**CI 安全：**GitHub Actions 官方文档要求审查第三方 Action、限制 `GITHUB_TOKEN` 权限并保护密钥。 [S4]

## 开源实战案例

**案例：Cosign 制品签名。**Cosign 是 Sigstore 项目提供的开源容器签名工具，可用于将“构建完成的镜像”与“签名/验证流程”连接起来。 [G1]

**案例：OpenSSF Scorecard。**Scorecard 是 OpenSSF 的开源项目，用于自动检查开源项目的若干安全实践，可作为供应链风险检查的参考工具，而不是替代人工风险判断。 [G2]

**案例：OWASP SAMM。**SAMM 提供软件安全成熟度模型，可作为团队建立安全治理改进项的参考。 [G3]

## 技术栈与选型要点

代码层使用 CodeQL/Semgrep 等 SAST，依赖层使用 OSV/SCA，秘密层使用 secret scanning，基础设施层使用 IaC 检查；工具选择应结合语言覆盖、误报处理、许可证和流水线时延。[S1][S7]  
SBOM 优先采用 SPDX 或 CycloneDX；SPDX 强调组件与许可证交换格式，CycloneDX覆盖组件、服务和漏洞等供应链信息。[S2][S4]  
SLSA provenance 用于描述构建来源和过程，Sigstore Cosign 可对容器或制品签名并验证；签名密钥和工作流身份必须遵循最小权限。[S3][G1][S7]

## 可复现案例

**案例 1：GitHub Actions 安全门禁。**在 PR 触发依赖、SAST、秘密和 IaC 检查；使用只读默认权限、固定 action SHA、环境审批和 OIDC，验收是未通过检查不能合并。[S7]  
**案例 2：SBOM 生成与漏洞回溯。**构建镜像时生成 SPDX/CycloneDX，上传到制品库并保存提交号；收到 CVE 后按组件版本筛选受影响服务，输出升级或缓解工单。[S2][S4]  
**案例 3：签名制品发布。**构建后使用 Cosign 签名并生成 provenance，部署侧仅允许验证通过且来源符合策略的镜像；验证失败走回滚路径。[S3][G1]

## 限制

扫描通过不等于没有漏洞；SBOM 可能遗漏运行时下载内容，provenance 也不能替代代码审查和渗透测试，因此应组合多层控制。[S1][S2][S5]

## 国内招聘技术栈证据

拜耳的两个 DevSecOps Engineer 职位是本岗位的同名招聘证据；其中 J1 的岗位描述涉及 AWS、Azure、GCP、Terraform、CloudFormation、Ansible、Chef、Kubernetes、Docker、CI/CD、安全扫描、漏洞评估与监控告警。[J1][J2]

J3-J7 是 SRE/DevOps、云工程、容器监控和运维开发职位。它们可作为理解供应链安全工程师与运行保障团队协作接口的国内样本，但 SBOM、签名、provenance 和安全门禁的技术要求仍以标准与开源工具文档为准。[J3][J4][J5][J6][J7][S1][S2][S3]
