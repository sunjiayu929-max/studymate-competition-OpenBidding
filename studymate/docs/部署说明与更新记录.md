# StudyMate 部署说明与更新记录

本文是 StudyMate 主系统、独立 AI 面试服务和独立 Hydro OJ 的部署记录。部署采用三个并列的 Docker Compose 项目：主系统负责前端、FastAPI、Caddy 和 Piston；AI 面试服务负责 Flask、面试上传文件和独立 MySQL；OJ 服务负责 Hydro Web、HydroJudge、题库和独立 MongoDB。跨服务只通过签名 API 和共享 Docker 网络通信。

本文不保存任何真实密钥、密码、Cookie、数据库内容或完整环境文件。每次部署更新都在本文末尾追加一条记录，不覆盖已有记录。

## 3. 标准更新流程

### 3.1 更新前

1. 确认本地目标分支和两个远端仓库状态。
2. 运行主系统后端测试、前端 lint/build，以及 AI 面试服务测试。
3. 查看当前生产容器和磁盘空间。
4. 备份主系统 SQLite、私有知识库、AI MySQL 和 AI 上传文件。
5. 记录将要发布的主仓库提交和 AI 面试仓库提交。

主系统和 AI 面试服务必须使用可追溯的 Git 提交或不可变镜像标签。不要只依赖 `latest` 作为回滚依据。

### 3.2 同步代码

从 `StudyMate` 父目录同步代码时，排除 Git 元数据、虚拟环境、依赖缓存、本地数据库和真实环境文件。不要用 `rsync --delete` 覆盖服务器上的三个环境文件或服务器备份目录。

### 3.3 部署

```bash
ssh -F /dev/null -o IdentitiesOnly=yes \
  -i ~/.ssh/studymate_deploy \
  deploy@121.40.64.199

cd /home/deploy/studymate
bash scripts/deploy.sh preflight
SKIP_PISTON_INIT=1 bash scripts/deploy.sh up
bash scripts/deploy.sh status
```

`up` 会先更新主系统并创建 `studymate_edge`，再构建和启动 AI 面试服务。普通更新不能使用 `docker compose down -v`，否则会删除命名卷中的业务数据。

发现并需要后续处理：

1. **P0：公网端口映射需要确认。**服务器上的 Caddy 当前监听宿主机 `8088/8443`，宿主机 `80/443` 没有监听；而标准文档和 Caddy 自动 HTTPS 预期使用 `80/443`。通过 SNI 直连 `8443` 可以验证 `/api/ping` 和 `/interview/health`，但从外部直接访问域名的链路仍依赖云端端口转发。必须确认安全组、负载均衡或 NAT 是否配置为公网 `80 -> 8088`、`443 -> 8443`；确认前不要擅自切换端口。
2. **P0：主系统启动时仍会修复固定演示账号。**[`backend/app/main.py`](../backend/app/main.py) 的 `_ensure_seed_users` 会在每次启动时写入固定的管理员、评委和学生账号信息，生产环境应增加显式的 `SEED_DEMO_USERS=0` 开关，默认关闭，并单独提供一次性演示数据初始化命令。
3. **P1：部署失败时没有自动回滚。**当前 `scripts/deploy.sh up` 会先重建主系统，再启动 AI 服务；任一阶段失败都可能形成“主系统已更新、面试服务未更新”的部分发布。需要增加部署锁、版本记录、更新前备份、健康检查失败回滚和明确的回滚命令。
4. **P1：健康检查只覆盖进程可用性。**主系统 `/api/ping` 不检查数据库，AI `/health` 也不检查 MySQL。建议新增数据库 readiness 检查，并让 Docker healthcheck 和部署验收同时检查数据库连接、迁移状态和共享 API。
5. **P1：数据库迁移仍在应用启动阶段执行。**主系统使用 `create_all`、SQLite 轻量 `ALTER`；AI 服务在 Flask 导入时执行迁移。生产环境应迁移到显式、可审计、可回滚的 Alembic/迁移命令，避免多个副本同时启动时竞争迁移。
6. **P1：面试报告回传失败依赖用户手动重试。**AI 服务当前把回调失败记为 `failed`，由页面上的 retry 入口再次触发。应增加持久化 outbox 或定时重试任务，保证浏览器关闭、短时网络故障时报告仍能回写主系统。
7. **P1：AI 旧版路由仍保留大量调试输出和 legacy 业务逻辑。**当前 Caddy 白名单没有公开这些 root-level legacy 路由，但代码中的 `print(session)`、异常原文输出和旧 Socket.IO 流程仍可能泄露敏感上下文或在误配置时放大风险。应统一结构化日志、移除会话/简历/LLM 原文输出，并把 legacy 路由隔离或下线。
8. **P2：镜像和依赖使用可变版本。**Compose 使用 `latest`、`mysql:8.0` 等可变标签，Python 依赖也使用兼容范围。应在发布清单中固定镜像 digest、Python lock 文件和前端 lock 文件，减少同一提交重复部署结果不一致的问题。
9. **P2：资源和日志治理不完整。**AI 服务、MySQL 和主系统主要容器没有统一的 CPU/内存上限及 Compose 日志轮转策略。服务器当前约有 8 GB 可回收 build cache，后续应增加维护窗口清理、日志上限和服务资源预算，避免面试并发拖垮主系统。
10. **P2：面试根路径行为与文档需要统一。**当前 `/interview` 会重定向，但 `/interview/` 被白名单返回 `404`；实际学习者流程从带 ticket 的 `/interview/integrations/studymate/launch` 进入。要么增加明确的面试入口页，要么把文档入口改成启动票据 URL，不能同时宣称 `/interview/` 是可用首页。
11. **P2：上传文件需要生命周期清理。**学习者简历按身份目录保存，删除接口会删除文件，但异常中断、重复上传和历史 soft-delete 文件仍需要定期清理任务，并在备份策略中记录保留周期。
12. **P2：生产 Caddy 缺少 HSTS 和更完整的安全响应头。**确认公网 HTTPS 和所有业务子资源均已稳定后，可增加 HSTS、`X-Frame-Options`/`frame-ancestors`、Permissions Policy 等配置，并先用报告模式验证兼容性。

## 6. 回滚原则

回滚只恢复应用版本，不删除数据卷：

1. 先保留当前日志、容器状态和数据库备份。
2. 将主系统和 AI 服务恢复到同一组已验证的提交或镜像版本。
3. 运行 `preflight`、启动并等待全部 healthcheck 通过。
4. 验证 `/api/ping`、`/interview/health` 和登录后面试流程。
5. 只有确认数据损坏且已有可用备份时，才进入数据库恢复流程；数据库恢复必须单独审批和记录。

禁止使用以下命令作为普通版本回滚：

```bash
docker compose down -v
docker system prune -a
```

这些命令可能删除业务数据、上传文件、Piston runtime 或仍可用于回滚的镜像。
